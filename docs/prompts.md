# 关键 Prompt 与人工审查记录

本文选取项目开发过程中最具代表性的 5 类问题，展示我如何向 AI 提供上下文、约束输出、定义验收标准，并对结果进行人工审查。

## Prompt 1：先拆解需求，再确定架构与交付计划

### 场景与目标

项目刚开始时，首先要避免直接让 AI 生成大量代码。我需要先确认题目中的必做项、加分项、范围边界和验证方式，再决定技术架构与实施顺序。

### Prompt

```text
你是一名负责技术方案和工程交付的资深全栈工程师。请先阅读股票模拟交易系统题目，此阶段不要写业务代码。

项目约束：
1. 前端必须使用 Vue 3 + TypeScript，后端使用 Node.js + Express，实时通信使用原生 WebSocket。
2. 用户、会话、行情、订单、持仓和成交都保存在单个进程内存中，重启丢失，不引入数据库和消息队列。
3. 必须实现限价单、价格优先/同价时间优先撮合、资金与持仓结算，以及行情和用户私有状态推送。
4. 同时完成 Docker、撮合测试和 WebSocket 断线恢复三个加分项。
5. README 必须让面试官在 3 分钟内启动项目。

请按以下格式输出：
A. 需求矩阵：必做、加分、不做，每项附可验证的验收条件；
B. 仍需人工决定的歧义点，不要自行假设；
C. 提供 2～3 种架构方案及取舍，并推荐一种；
D. 按依赖顺序拆分实施任务，每个任务列出输入、输出、测试和完成标准；
E. 列出最容易被 AI 写错的 5 个风险点。

方案需要控制在 1～3 天可交付范围内，优先保证撮合和资产正确性，不为了“架构先进”引入题目不需要的基础设施。
```

### Prompt 设计思路

- 先限制阶段为“只设计、不写代码”，防止 AI 跳过需求分析直接生成脚手架。
- 把技术栈、内存边界、加分项和启动时间写成硬约束。
- 要求输出需求矩阵和可验证的验收条件，让后续测试能够追溯到题目。
- 明确要求暴露歧义、比较方案和列出风险，而不是只给一个看似确定的答案。

### AI 建议摘要

AI 建议采用 npm workspaces 管理的 TypeScript 模块化单体：前端、后端和共享契约分包，但撮合、结算和事件提交保留在同一 Node.js 进程的同步调用链中；先实现共享模型和领域测试，再接入 HTTP、WebSocket、前端和部署。

### 我的审查与最终调整

我确认模块化单体符合内存题目的规模，同时将“真实用户互相撮合 + 系统账户补充流动性”纳入范围，让单用户演示和双用户成交都可验证。我没有采用微服务、数据库或消息队列，因为它们增加交付风险，却不能提高本题核心评分。

### 验证证据

- 需求与架构追溯：<code>README.md</code> 的功能、架构、测试和已知限制章节
- 工程边界：<code>apps/</code>、<code>packages/shared/</code> 的模块划分，以及根目录构建和质量脚本
- 交付证据：<code>Dockerfile</code>、<code>docker-compose.yml</code> 和各领域测试文件

## Prompt 2：设计可证明正确的撮合与资产结算

### 场景与目标

撮合引擎是项目风险最高的部分。仅要求 AI “实现价格时间优先”容易遗漏部分成交、价差退款、撤单释放、重复请求和失败回滚，因此需要先明确领域不变量。

### Prompt

```text
你是一名证券交易系统领域工程师。请为内存限价撮合模块设计可测试的领域规则，先给模型、算法和不变量，再给实现建议。

已知条件：
- 只支持 AAPL、MSFT、TSLA 的整股限价单；
- 买盘价格高者优先，卖盘价格低者优先，同价时服务端 sequence 小者优先；
- 成交价取先进入订单簿的 resting/maker 订单价格；
- 买单下单前冻结“限价 × 数量”，卖单冻结委托数量；
- 禁止透支和做空，价格和资金使用安全整数的最小货币单位；
- 支持部分成交、跨多档成交、撤单和真实用户自成交防护；
- 系统流动性账户必须走普通订单和结算路径，不能获得特殊优先级；
- 使用“userId + clientOrderId”处理不确定网络重试。

请输出：
1. Order、Trade、Account 的最小字段和状态转换；
2. 买卖盘比较器和撮合伪代码；
3. 预冻结、部分成交、价格改善退款、撤单释放的计算规则；
4. 一组具体数字示例：买方限价 105.00、卖方挂价 102.00、发生部分成交时双方资产如何变化；
5. 命令执行中任一步失败时需要回滚的状态清单；
6. 单元测试矩阵，至少覆盖价格优先、时间优先、maker 价、部分成交、多笔成交、STP、幂等和结算失败回滚。

请主动寻找会导致负余额、重复成交、金额溢出或订单簿优先级被破坏的边界条件。不要用浮点数直接计算资金。
```

### Prompt 设计思路

- 先声明领域规则和不变量，减少 AI 自行发明交易语义。
- 要求给出数字例子，迫使模型把冻结、成交和退款计算落到可检查结果。
- 将异常回滚和幂等纳入同一个 Prompt，而不是只验证正常成交路径。
- 直接要求测试矩阵，使算法描述能转化为自动化证据。

### AI 建议摘要

AI 将职责拆为 <code>OrderBook</code>、<code>AccountLedger</code> 和 <code>OrderService</code>：订单簿只计算成交，账本独占资产写入，订单服务协调冻结、撮合、结算、幂等记录、事件发布和命令级回滚。

### 我的审查与最终调整

我重点检查了三个容易被忽略的点：部分成交后的剩余冻结必须仍按买方限价计算；成交价改善要立即退款；真实用户遇到自己的最优对手盘时不能跳过该订单破坏优先级，因此当前 STP 策略是取消新订单剩余量并释放冻结资产。系统账户虽然免于真实用户 STP，但仍遵守普通价格—时间排序。

### 验证证据

- <code>apps/server/src/matching/order-book.test.ts</code>
- <code>apps/server/src/accounts/account-ledger.test.ts</code>
- <code>apps/server/src/orders/order-service.test.ts</code>

## Prompt 3：解决 WebSocket 重连期间的快照与增量竞态

### 场景与目标

“断线后自动重连”并不等于状态正确。若先请求快照再连接 WebSocket，两者之间的事件可能丢失；若先连接但不缓冲，快照又可能覆盖刚收到的新事件。我需要 AI 明确设计恢复协议，而不是只写一个重试定时器。

### Prompt

```text
你是一名负责实时系统一致性的工程师。请设计本项目的 WebSocket 断线恢复协议，目标是页面刷新、短暂断网、重复消息和连接竞态后，前端最终状态与服务端一致。

系统现状：
- REST 用于下单、撤单和 GET /api/bootstrap 完整快照；
- WebSocket 推送 market.updated、order.updated、account.updated、trade.created；
- 事件有唯一 eventId 和全局单调递增 stateVersion；
- 私有事件只发给相关用户，因此单个客户端看到的 stateVersion 可以跳号，不能要求版本连续；
- HttpOnly Session Cookie 同时用于 REST 和 WebSocket 鉴权。

请设计并说明：
1. connection.ready、业务事件、heartbeat 的协议字段和职责；
2. “先连接并缓冲事件，再请求快照”的完整状态机和伪代码；
3. 快照返回后如何排序、去重并应用比快照更新的缓冲事件；
4. 如何处理同 eventId 不同版本、同版本不同 eventId、已知事件格式损坏、旧连接迟到回调；
5. 指数退避、抖动、存活超时、服务端 ping/pong 和慢客户端背压；
6. 401/1008 会话失效为何必须停止重试并清理身份；
7. 针对每个竞态编写确定性测试，不使用真实 sleep。

不要假设 WebSocket 建连成功就已经同步完成；只有快照与缓冲增量归并成功后，连接状态才能进入 live 并重置退避次数。
```

### Prompt 设计思路

- 明确指出版本允许跳号，避免 AI 套用“必须 version + 1”的错误逻辑。
- 将恢复过程表达为状态机，并要求处理重复、冲突、旧 generation 和终止性错误。
- 把传输存活与业务同步分开：WebSocket 打开不代表本地数据已经可信。
- 要求使用可注入时钟、随机数和定时器，保证重连测试稳定、快速。

### AI 建议摘要

AI 建议将传输层和同步层分离：<code>RealtimeClient</code> 负责协议校验、存活检测和退避，<code>realtime-store</code> 负责连接 generation、事件缓冲、bootstrap 基线、冲突检测和状态归并。

### 我的审查与最终调整

我要求前端在同步阶段遇到冲突或损坏的已知事件时放弃本次基线并重新连接，而不是静默覆盖；<code>connection.ready</code> 的版本若高于随后取得的快照，也必须重新同步。E2E 模式固定重连抖动，但生产模式仍保留随机 jitter，避免为了测试稳定而改变生产行为。

### 验证证据

- <code>apps/server/src/realtime/realtime-hub.test.ts</code>
- <code>apps/web/src/api/realtime-client.test.ts</code>
- <code>apps/web/src/stores/realtime-store.test.ts</code>

## Prompt 4：让交易终端可操作，而不只是视觉上“像终端”

### 场景与目标

界面选择了专业交易终端风格，但评分重点仍是完整交易流程和状态正确性。因此 Prompt 需要同时约束信息架构、可访问性、金额输入和服务端权威状态。

### Prompt

```text
你是一名熟悉交易产品的 Vue 3 前端工程师。请基于现有 REST 和 WebSocket 契约设计一个响应式模拟交易终端，不修改后端交易规则。

页面必须包含：
- AAPL、MSFT、TSLA 行情列表和选中股票上下文；
- 最新价、涨跌幅、最佳买卖价和最近 60 秒走势；
- 限价、数量、买入/卖出、最佳价快捷填入；
- 可用/冻结资金、可用/冻结持仓；
- 委托、持仓、最近成交三个可键盘操作的标签页；
- WebSocket 连接状态、退出和错误提示。

关键行为约束：
1. 不对资金、持仓或成交做乐观更新，服务端事件是唯一权威来源；
2. 价格输入必须通过十进制字符串精确转换为“分”，不能使用 price * 100；
3. 一次下单意图生成一个 clientOrderId。网络错误或 5xx 后保留该 ID，明确 4xx、成功或输入变化后才生成新 ID；
4. 提交失败保留用户输入，避免重复点击；撤单成功后等待 order.updated 再解除按钮锁定；
5. 涨跌不能只依赖红绿色，必须同时提供符号和文本；
6. 桌面端采用行情、交易、资产三栏，窄屏按操作顺序纵向排列。

请输出组件树、Pinia store 职责、页面状态转换、错误处理策略和组件测试清单。先说明数据流，再给实现。
```

### Prompt 设计思路

- 将视觉目标和行为目标一起写入，防止 AI 只生成漂亮但不可用的页面。
- 明确服务端权威，避免组件自行猜测成交和余额。
- 把金额精度、幂等意图和失败路径直接写成前端约束。
- 要求组件树和 store 职责，控制 <code>TradeView</code> 不演变为包含全部业务逻辑的巨型组件。

### AI 建议摘要

AI 将页面拆为股票栏、行情与下单区、资产区、活动标签页，并把身份、交易快照和实时同步拆到独立 Pinia store。下单和撤单通过 REST 发命令，WebSocket 事件更新展示状态。

### 我的审查与最终调整

我保留了专业终端布局，但补充了键盘可访问的标签页、非颜色涨跌表达、失败后保留输入、撤单权威确认和未授权统一跳转。价格解析使用字符串与 <code>BigInt</code>，避免十进制浮点误差；页面没有直接修改账户余额。

### 验证证据

- <code>apps/web/src/components/OrderForm.test.ts</code>
- <code>apps/web/src/components/TerminalComponents.test.ts</code>
- <code>apps/web/src/views/TradeView.test.ts</code>
- <code>e2e/paper-trading.spec.ts</code>

## Prompt 5：把 AI 产出当作待审查代码，而不是最终答案

### 场景与目标

功能基本完成后，需要以面试官和代码审查者视角重新检查实现。目标不是让 AI 总结“项目已完成”，而是要求它寻找反例、给出证据，并明确区分通过、失败和无法验证。

### Prompt

```text
你是一名严格的高级代码审查者。请把当前仓库视为未经验证的候选人提交，对照题目和设计规格做证据驱动审查。不要因为已有测试或 README 声明就默认功能正确，也不要先修改代码。

审查重点：
1. 撮合价格—时间优先、部分成交、maker 价和资产不变量；
2. trade.created 是否只投递给买卖相关用户，系统账户是否绕过普通优先级；
3. 所有 ID 是否符合共享 UUID 契约，金额计算是否可能越过安全整数；
4. 行情 tick、系统流动性刷新和长期历史测试是否真的推进时间并验证失败恢复；
5. 下单重试是否正确复用 clientOrderId，401/1008 是否停止重连；
6. SPA fallback 是否可能被编码后的 /api、/ws、点段或反斜杠路径绕过；
7. E2E 的随机 jitter、时钟和行情是否导致偶发失败；
8. README 的启动和 Docker 声明是否与实际验证证据一致。

输出格式：
- 先列发现，按严重度排序；每项给出文件/位置、失败场景、为什么有风险、最小复现或应补的测试；
- 不确定的结论标为“待验证”，不能写成“通过”；
- 然后给最小修复建议，避免无关重构；
- 最后列出必须运行的质量门：format、lint、typecheck、unit/integration、build、E2E、Docker，并分别报告真实退出结果。
```

### Prompt 设计思路

- 给 AI 设定“怀疑者”角色，并禁止先修改，避免它为了完成任务而掩盖问题。
- 指定高风险检查清单和统一发现格式，让结论可以复现，而不是泛泛评价代码质量。
- 强制区分“通过”和“无法验证”，防止文档把未运行的 Docker 写成验收成功。
- 要求最小修复和回归测试，控制 AI 不借审查进行大范围重构。

### AI 建议摘要

审查发现和复核重点包括：私有成交事件 audience、系统流动性 UUID 契约、长期测试的时间推进、命令不确定性、会话终止、编码静态路径探测，以及 E2E 重连 jitter。

### 我的审查与最终调整

我没有直接接受 AI 的“可能有问题”判断，而是逐项用针对性测试裁决：已有正确行为则保留代码并补充证据；确认存在缺口时只做最小修正。Docker daemon 不可用时，我只记录已经完成的配置检查；环境恢复后再补验一键构建、容器启动、健康检查和容器内业务流程，并据此更新 README。

### 验证证据

- 对应修正均有单元或集成回归测试。
- 项目质量门包含 Prettier、ESLint、TypeScript、Vitest、生产构建和 Playwright。
- Docker Compose 一键构建、启动、健康检查和容器内业务流程已完成补验，复现命令记录在 README。

## 总结：我如何使用 AI

本项目中的 Prompt 不以“让 AI 一次写完”为目标，而是遵循以下循环：

```text
明确场景和约束
→ 要求结构化、可验证的输出
→ 人工检查领域语义和失败路径
→ 用测试或运行结果裁决
→ 只保留经过验证的方案
```

AI 主要帮助我提高方案生成、边界枚举和测试设计的速度；需求取舍、领域规则、风险判断和最终交付责任仍由我承担。
